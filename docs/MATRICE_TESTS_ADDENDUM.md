# Addendum à la matrice de validation G0–G11

Cet addendum complète la matrice source sans la modifier. Les IDs sont utilisés tels quels dans les futurs noms de tests et contrats ; les jeux sont synthétiques et les oracles en centimes entiers.

| ID | Gate | Scénario | Oracle / condition de succès | Niveau |
|---|---|---|---|---|
| IMP-11 | G3 | Import généré le jour même, date `Téléchargement du` ou date de réception de repli | Avec en-tête, `complete_through = min(coverage_through, generated_on - 1 jour)` ; sans date d'en-tête, le dernier jour avec opérations est provisoire et `complete_through = min(coverage_through, max(booked_on) - 1 jour)` ; la section sans opération n'affirme aucun jour complet ; les montants restent inclus dans les sommes brutes | integration |
| IMP-12 | G3 | Opération dont `booked_on` est hors période de sa section | `OUT_OF_PERIOD` bloque tout le fichier et la ligne n'entre pas dans le maximum automatique ; le preview exige une décision auditée `link_existing` ou `create_occurrence`, puis commit intégral | integration |
| IMP-13 | G3 | Deux sections d'un même fichier mappées sur le même `account_id` | fichier structurellement rejeté ; 0 transaction et 0 `source_row` commises ; des comptes distincts restent isolés | integration |
| IMP-14 | G3 | Base avec rangs `{1,3}` et fichier demandant 3 occurrences ; provenance invalide | `count(occurrence_rank) != max(occurrence_rank)` bloque l'import ; insertion directe du rang 3 sans rang 2 rejetée ; une source ne peut viser un autre compte/section, un import `no_op`/`rejected`, ni lier deux fois le même fichier à la même transaction | integration |
| MONEY-10 | G4 | `refund_of` entre mois et comptes, allocations et liens multiples | seul un lien `confirmed` actif contribue, à la date du crédit ; filtre multi-comptes exige source et achat dans le périmètre ; autres vues signalent l'avoir non attribué ; cumul lié par source `≤ Σ allocations refund`, par cible `≤ Σ |allocations expense|`; `target_allocation_id` cible une allocation expense précise ou la répartition prorata totalise le lien (ADR-007) | integration/golden |
| KPI-08 | G6 | Compte de rôle `personal` importé, modes `envelope` et `observed` | mode défaut `envelope` exclut les dépenses du compte personnel et garde `allocation_personal`; mode `observed` inclut les dépenses observées, exclut l'allocation, classe le crédit propre `transfer_owned` et montre le reliquat ; aucune dépense/enveloppe comptée deux fois | golden/contract |
| SEC-06 | G11 | Nouvelle connexion/pool SQLite et tentative `INSERT OR REPLACE` | chaque connexion pose `foreign_keys=ON` et `recursive_triggers=ON`; REPLACE et DELETE sur provenance/transactions protégées échouent par trigger ; le code applicatif n'emploie aucun `OR REPLACE`/`REPLACE INTO` | security/integration |
| IMP-02 (complément F-09) | G3 | Chevauchement A/B et inspection de provenance | chaque ligne source conserve son `row_sha256`, `section_index`, `logical_row_idx` et transaction cible ; aucun champ brut bancaire n'est modifié ; N provenances vers 1 transaction seulement lorsque la clé/rang correspond | integration |
| FULL-01 (complément F-09) | G11 | Import → décision humaine → règle/prompt → recalcul analytique → reimport → backup/restore | cardinalité et montants bancaires inchangés ; réimport et recalcul n'écrasent ni décision humaine confirmée ni allocation versionnée ; sauvegarde/restauration garde les mêmes KPI et décisions | e2e |
| KPI-07 (complément F-09) | G6 | Drilldown de chaque endpoint/métrique pour même filtre | formule, bornes, comptes, `mode`, `personal_mode`, catégorie/flux et exclusions sont identiques entre total et drilldown ; recomptage exact des contributions égal à `raw_cents`/`raw_basis_points`/`raw_count` ; liens `refund_of` inclus selon ADR-021 | contract |
| IMP-15 | G3 | Transitions et immutabilité d'import (ADR-019.d) | seul `previewed → committed|rejected` est permis ; un fichier `rejected` n'a aucune `source_row` ; fichier/sections commités et décisions d'aperçu sont immuables ; un `no_op` est terminal, référence le commit du même hash et ne conserve pas d'octets | integration |
| KPI-09 | G6 | Comparabilité des soldes (ADR-018.3 / ADR-024.2) | comparer uniquement les soldes d'en-tête tels que `balance_as_of <= complete_through`, si l'union des jours complets couvre `(D0,D1]` ; résultat déterministe par date indépendamment de l'ordre d'import ; `mismatch` rend la complétude du mois `unknown` | contract/golden |
| IMP-16 | G3 | Provenance par identité au commit (ADR-019.c) | pour chaque clé d'identité d'un import, le service exige `count(source_rows) = n_new`; chaque source cible une transaction de même `identity_key_sha256`; au total `source_rows = parsed_operation_count` et toute transaction a une provenance | integration |
| SEC-07 | G11 | Liaison Python des montants (ADR-019.h) | seuls les objets dont `type(value) is int` sont liés comme centimes ; `bool`, `float` (même intégral) et texte sont rejetés avant SQL | unit/security |
| API-02 | G0 | Correspondance anomalies des fixtures et codes REST (n-13) | les codes ci-dessous sont exposés tels quels ou traduits explicitement ; warning, blocage de preview et rejet structurel ne sont pas confondus | contract |
| MONEY-11 | G4 | Remboursements ciblés et proratisés sur les mêmes allocations expense | un lien proratisé confirmé matérialise exactement les parts ADR-007 ; service et trigger SQL refusent le scénario prorata 10 000 puis ciblé 8 000 sur une allocation de 10 000 ; chaque séquence acceptée garde chaque net catégorie ≥ 0 et `Σ net = Σ expense − Σ liens confirmés` | integration/property/schema |
| MONEY-12 | G4 | Retrait auditable d'allocations et restauration de décision | `clear_allocations` écrit `retracted_at_utc`, `retracted_by_decision_id`, décision et audit ; calcule le résidu complet, avance la version et est idempotent au même état ; une proposition touchée par le retrait est rejetée/auditée dans la même transaction ; un lien confirmé actif protège toujours ses allocations ; `before_json` peut être restauré par de nouvelles allocations | integration |
| MONEY-13 | G4 | Défense de périmètre au niveau SQL | insertion SQL brute d'un `refund_of` source/cible entre comptes différents échoue ; la mutation du schéma qui retire la comparaison `account_id` échoue à `verify_schema.py` | security/integration |
| MONEY-14 | G4 | Versions, concurrence et idempotence des liens | proposition identique et confirmation rejouée ne dupliquent ni lien ni audit ; version périmée → `VERSION_CONFLICT` ; une supersession conserve `source_allocation_id` et un rejeu avec une autre source est un conflit ; confirmations concurrentes produisent une seule transition/audit ; remplacements concurrents ont un seul gagnant et un état actif conforme | integration/concurrency |
| MONEY-15 | G4 | Prorata borné par méthode des plus grands restes | propriétés sur 1..8 catégories, montants de 1 centime à grands montants et ordres permutés : parts entières déterministes, `Σ parts = montant`, chaque part dans `[0, capacité restante]`; cas 4 × 2 500 et lien de 2 centimes ne crée aucune part négative ou excessive | unit/property |
| MONEY-16 | G4 | Proposition dont une jambe change avant rejet manuel | réallocation/retrait de la source ou de la cible rejette la proposition et écrit l'audit `reason=allocation_changed`; le lien reste rejetable et `clear_allocations` ne reste jamais bloqué; zéro `IntegrityError` brute | integration/fuzz |
| MONEY-17 | G4 | Grille des entrées publiques allocations/remboursements | entrées invalides et conflit SQLite à la clé active de `replace_refund_link` renvoient une `AppError` 409 au code métier stable ; aucune entrée publique ne laisse remonter `IntegrityError` | integration |
| MONEY-18 | G4 | Contraintes SQL des parts matérialisées | la somme des parts égale le lien confirmé ; chaque part est entière, positive et vise une allocation expense active du même achat ; plafonds ciblés + prorata sont combinés ; `UPDATE` et `DELETE` de part sont refusés ; le retrait d'un garde-fou fait échouer un mutant `verify_schema.py` | schema/mutant |
| MONEY-19 | G4 | Machine d'états des liens refund en SQLite | insertion en `proposed` seulement puis `proposed → confirmed|rejected` ; `confirmed → proposed|rejected`, `rejected → confirmed|proposed` échouent ; retrait des triggers détecté par mutants | schema/mutant |
| MONEY-20 | G4 | Refus conservateur quand le prorata est infaisable | si le total des capacités expense restantes est inférieur au lien, service et fonction domaine refusent `REFUND_PRORATA_INFEASIBLE`; aucun lien confirmé ni part tronquée n'est écrit | unit/integration |
| MIG-FREEZE-01 | G4 | Gel de la première migration réelle | SHA-256 des fichiers Python et SQL `0001` égaux aux empreintes de HEAD `1066748`; tout changement échoue avec « migration gelée, créer 0003 » | integration |
| MIG-0002-01 | G4 | Upgrade non vide depuis 0001 | conserve les lignes comptes/transactions/provenance/allocations/décisions/liens de chaque état ; crée la sauvegarde préalable `0600`; réinstalle les triggers ; `integrity_check=ok`, `foreign_key_check` vide et `sqlite_master` égal à `schema.sql` | integration |
| KPI-03 (complément T17) | G6 | Somme analytique par catégorie après avoir multi-catégories au niveau service | `Σ net_effect_by_category.by_category_cents = coût expense initial − remboursements confirmés`, au centime près ; le remboursement catégoriel somme exactement au montant lié | integration/contract |
| KPI-07 (complément T17) | G6 | Recomposition du total service depuis les parts de remboursement matérialisées | le drilldown par catégorie relit les parts du lien confirmé, leurs centimes totalisent le lien, et la somme des catégories égale le total analytique sous les mêmes filtres | integration/contract |

### Correspondance codes fixtures ↔ API

| Code fixture | Code API / niveau | Effet et résolution |
|---|---|---|
| `MISSING_PERIOD` | `SECTION_RANGE_REQUIRED` · erreur bloquante | Le preview reste résoluble ; l'utilisateur fournit `coverage_from` et `coverage_through` par PATCH de section avant le commit intégral. |
| `DUPLICATE_ACCOUNT_SECTION` | `DUPLICATE_ACCOUNT_SECTION` · erreur structurelle | Deux sections du même fichier visent le même compte ; le fichier passe `rejected`, avec zéro transaction et zéro `source_row`. |
| `PROVISIONAL_DAY` | `PROVISIONAL_DAY` · avertissement | La journée reste dans les montants bruts mais hors des jours complets ; elle ne bloque pas le commit à elle seule. |
| `OUT_OF_PERIOD` | `OUT_OF_PERIOD` · résolution requise | La ligne ne participe pas au maximum automatique ; PATCH de multiplicité exige `link_existing` ou `create_occurrence`, puis commit tout-ou-rien. |
| `ZERO_AMOUNT` | `VALIDATION_ERROR` avec détail `ZERO_AMOUNT` · erreur bloquante | Le format CA ne crée aucune transaction/source pour la ligne ; le fichier doit être corrigé ou rejeté. |

### Tests supplémentaires T19 — règles, ordre et simulation

| ID | Gate | Scénario | Oracle / condition de succès | Niveau |
|---|---|---|---|---|
| RULE-10 | G4 | Règles versionnées et marketplaces ambiguës | Brouillon → approbation → édition/désactivation avance la version ; version périmée → `VERSION_CONFLICT` ; marketplace globale sans justification, motif de libellé et contrainte additionnelle distincte → `AMBIGUOUS_MARKETPLACE_GLOBAL_SCOPE` | integration |
| RULE-11 | G4 | Priorité humaine, ordre des règles et conflit à priorité égale | Une décision humaine reste gagnante ; priorité numérique la plus basse gagne ; deux actions divergentes au même rang n'ont aucun gagnant automatique et signalent le conflit | integration |
| RULE-12 | G4 | Dry-run d'une règle ratio et pagination | Aucun contenu des tables ne change ; IDs, avant/après, sommes en centimes et totaux par catégorie sont cohérents ; ADR-007 conserve la somme au centime | integration |
| RULE-13 | G4 | Application, import chevauchant et rejeu | Une règle ne remplace pas une allocation humaine après ajout d'une `source_row` ; origine `rule`, audit et exécution sont tracés ; le second appel ne modifie aucune table | integration |
| RULE-14 | G4 | Exception durable par transaction | L'exception garde auteur/motif/horodatage et avance la version ; la modification du motif est auditée avant/après ; la transaction exclue reste non classée après simulation et application | integration |
| RULE-15 | G4 | Motif adversarial de libellé | Les motifs sont des fragments littéraux bornés, compilés après échappement ; limite de longueur/jokers rejetée ; une entrée de type regex n'exécute pas de quantificateur arbitraire | unit/security |
| RULE-16 | G4 | Propriété seedée sur au moins 1000 opérations règle/décision/import | Une décision manuelle déjà prise reste identique après toute règle ou source de réimport ; chaque allocation conserve le signe et `Σ allocations + résidu = montant bancaire` | property/integration |
| RULE-17 | G4 | Simulation de 10000 transactions | Temps mesuré ; plafond visible ; pagination stable ; aucune allocation, règle exécutée ou ligne d'audit ajoutée | performance/integration |
| RULE-18 | G4 | Mémoire exacte, heuristique et LLM | Une mémoire exacte validée précède les suggestions heuristique et LLM ; ces suggestions ne créent pas d'allocation | integration |
| RULE-19 | G4 | Prédicats compte, direction, montant, dates et flux | Seules les transactions satisfaisant chaque contrainte entière explicite sont proposées | integration |
| RULE-20 | G4 | Marketplace ambiguë détectée depuis un motif sans payee lié | Le libellé synthétique correspondant à une marketplace connue est marqué ambigu dans la simulation | integration |
| RULE-21 | G4 | Plafond d'exceptions de règle | L'ajout d'une exception au-delà de la limite configurée échoue sans avancer la version ni modifier la règle | integration |
