# Addendum à la matrice de validation G0–G11

Cet addendum complète la matrice source sans la modifier. Les IDs sont utilisés tels quels dans les futurs noms de tests et contrats ; les jeux sont synthétiques et les oracles en centimes entiers.

| ID | Gate | Scénario | Oracle / condition de succès | Niveau |
|---|---|---|---|---|
| IMP-11 | G3 | Import généré le jour même, date `Téléchargement du` ou date de réception de repli | `generated_on` provient de l'en-tête si présent, sinon de la réception ; chaque jour `>= generated_on` est `provisional` mais reste inclus dans les sommes brutes ; `complete_through = min(coverage_through, generated_on - 1 jour)` ; mois jamais marqué `complete` sur ce jour | integration |
| IMP-12 | G3 | Opération dont `booked_on` est hors période de sa section | `OUT_OF_PERIOD` bloque tout le fichier et la ligne n'entre pas dans le maximum automatique ; le preview exige une décision auditée `link_existing` ou `create_occurrence`, puis commit intégral | integration |
| IMP-13 | G3 | Deux sections d'un même fichier mappées sur le même `account_id` | fichier structurellement rejeté ; 0 transaction et 0 `source_row` commises ; des comptes distincts restent isolés | integration |
| IMP-14 | G3 | Base avec rangs `{1,3}` et fichier demandant 3 occurrences ; provenance invalide | `count(occurrence_rank) != max(occurrence_rank)` bloque l'import ; insertion directe du rang 3 sans rang 2 rejetée ; une source ne peut viser un autre compte/section, un import `no_op`/`rejected`, ni lier deux fois le même fichier à la même transaction | integration |
| MONEY-10 | G4 | `refund_of` entre mois et comptes, allocations et liens multiples | seul un lien `confirmed` contribue, à la date du crédit ; filtre multi-comptes exige source et achat dans le périmètre ; autres vues signalent l'avoir non attribué ; somme liée par source `≤ crédit`, par cible `≤ |achat|`, source = crédit `refund`, cible = débit `expense` | integration/golden |
| KPI-08 | G6 | Compte de rôle `personal` importé, modes `envelope` et `observed` | mode défaut `envelope` exclut les dépenses du compte personnel et garde `allocation_personal`; mode `observed` inclut les dépenses observées, exclut l'allocation, classe le crédit propre `transfer_owned` et montre le reliquat ; aucune dépense/enveloppe comptée deux fois | golden/contract |
| SEC-06 | G11 | Nouvelle connexion/pool SQLite et tentative `INSERT OR REPLACE` | chaque connexion pose `foreign_keys=ON` et `recursive_triggers=ON`; REPLACE et DELETE sur provenance/transactions protégées échouent par trigger ; le code applicatif n'emploie aucun `OR REPLACE`/`REPLACE INTO` | security/integration |
| IMP-02 (complément F-09) | G3 | Chevauchement A/B et inspection de provenance | chaque ligne source conserve son `row_sha256`, `section_index`, `logical_row_idx` et transaction cible ; aucun champ brut bancaire n'est modifié ; N provenances vers 1 transaction seulement lorsque la clé/rang correspond | integration |
| FULL-01 (complément F-09) | G11 | Import → décision humaine → règle/prompt → recalcul analytique → reimport → backup/restore | cardinalité et montants bancaires inchangés ; réimport et recalcul n'écrasent ni décision humaine confirmée ni allocation versionnée ; sauvegarde/restauration garde les mêmes KPI et décisions | e2e |
| KPI-07 (complément F-09) | G6 | Drilldown de chaque endpoint/métrique pour même filtre | formule, bornes, comptes, `mode`, `personal_mode`, catégorie/flux et exclusions sont identiques entre total et drilldown ; recomptage exact des contributions égal à `raw_cents`/`raw_basis_points`/`raw_count` ; liens `refund_of` inclus selon ADR-021 | contract |
